# 07. The AI subsystem

## 1. The division of labour

AI does the **search**. Deterministic code does the **judgement**.

The search half finds the repository and commit behind a published artifact, works out how it was
built, and repairs a build that fails. All three run open-ended and evidence-driven, and all three
tolerate a wrong first answer because the answer is *checkable*. Modern models handle that shape
well.

The judgement half, meaning execute, normalize and compare, is what the product sells. It runs
deterministically, with no model in reach, and the crate graph gives it no way to call one
([`01-architecture.md`](01-architecture.md) §2.2).

So **AI reduces cost and extends coverage here. It does not establish correctness.** Point every
model in the system at a random-text generator and Trigon produces fewer verdicts rather than wrong
ones.

## 2. Three roles, one real agent

An earlier draft proposed four agents. Two of them were doing something other than search:

| Role | The work it does | Shape |
|---|---|---|
| **Resolver** | About 95% a deterministic lookup | A ladder of deterministic rungs, with a model as the last resort |
| **Builder** | Open-ended search | **The one real agent** |
| **Explainer** | Classification over a near-closed taxonomy | A deterministic classifier, with a model for `Unknown` |
| **Triage** | Natural-language query over results | Deferred, see [`11-interfaces.md`](11-interfaces.md) §4 |

We merged the earlier "StrategySmith" and "BuildDoctor" into one **Builder** on purpose. They
shared tools, output type and validation, and differed over whether `prior_attempts` was empty.
Keeping them apart would have bought two prompt families, two eval sets, two budget configurations
and two regression surfaces for one capability.

### 2.1 Resolver

A ladder, cheapest first. A model gets a turn once every deterministic rung has failed.

1. Registry metadata (`repository.url`, `project_urls`, `.nuspec` repository element).
2. **Published provenance** ([`06-ci-awareness.md`](06-ci-awareness.md) §5), giving repo *and*
   commit for one API call.
3. Ecosystem-specific strong signals: npm's `gitHead`, crates' `.cargo_vcs_info.json`, NuGet's
   SourceLink PDB data.
4. Exact tag → `v`-prefixed tag → fuzzy version-in-tag.
5. Manifest history: the first commit where the manifest version differs from all parents.
6. **Tree-hash scoring.** Take commits in a window around the publish time, hash each subtree, and
   score it against the file set and content hashes of the published sdist or tarball, excluding
   known-generated files. Rank by score.
7. A model, with search-style tools.

Rung 6 deserves emphasis. **It is an algorithm, and it beats any prompt at this task.** Ask a model
which commit a tarball came from and it guesses. A tree-hash comparison measures. Building rung 6
well returns more than any amount of prompt engineering on rung 7.

We record the rung that produced the answer as `SourceDiscovery`
([`02-domain-model.md`](02-domain-model.md) §1), because it predicts a false result better than
anything else we have.

### 2.2 Builder

The one real agent. It proposes a `Strategy` from a target, a source tree, the evidence, the CI
recipe, and, on repair iterations, the prior attempt and its failure.

**Tools**, all read-mostly and scoped to the run's own workspace:

| Tool | Notes |
|---|---|
| `list_repo_files(glob)` | Over the pinned checkout |
| `read_repo_file(path, range)` | Bounded. Large files truncate with a marker. |
| `read_build_log(tail_bytes)` | **Compressed first**, see §4.2 |
| `read_ci_workflow(path)` | The parsed `CiRecipe` rather than raw YAML |
| `list_registry_versions(package)` | Sibling versions, for strategy reuse |
| `get_evidence()` | The `Intrinsics` evidence list and the toolchain resolution |
| `run_in_container(cmd)` | **Exploration environment only** (§3), never verification |

It **outputs** a typed `Candidate { strategy, rationale, confidence, provenance }`, which passes
the validation in [`04-strategies.md`](04-strategies.md) §7 before we accept it.

### 2.3 Explainer

Given a `Divergent` comparison, classify each remaining difference. The deterministic classifier
runs first over a near-closed taxonomy: timestamps, entry ordering, permissions and umask, embedded
absolute paths, compression level, line endings, build-id and UUID and MVID, embedded version
metadata, locale formatting, and map iteration order. Those cover most real mismatches, and the model
handles `Unknown`.

Two constraints:

- **It cannot change a verdict.** It annotates, and it has no path to promoting a mismatch to a pass.
  Calling it a judge would misdescribe it. It explains diffs, and it is a UI feature.
- **Its prose stays out of every signed document** ([`09-attestations.md`](09-attestations.md) §4).
  The *deterministic* difference signature goes in. The explanation lives in the database and the UI
  with its model id attached.

Over time its value shows up as a **stabilizer proposer**. It says that a difference is a build
timestamp in `META-INF/MANIFEST.MF` and offers a candidate custom stabilizer with a draft `reason:`.
That goes to a corpus-wide impact preview, then human review, then a definitions pull request. Build
that loop, and note that the mandatory `reason:` field exists to protect it.

## 3. Exploration is not verification

Taken from the prior art, whose scratch-VM design gets this right and states it more sharply than
"bounded retries plus a clean re-run":

```
┌─ EXPLORATION environment ────────────────┐   ┌─ VERIFICATION environment ─────────┐
│ • agent may exec, poke, re-run           │   │ • no exec, no agent, no model      │
│ • wider tooling, live container retained │   │ • declared egress tier only        │
│ • output is NEVER attestable             │──▶│ • output is the ONLY attestable    │
│ • its job is to produce a candidate      │   │   artifact                         │
└──────────────────────────────────────────┘   └────────────────────────────────────┘
```

A strategy leaves exploration as **data**. Then the confirmation policy decides how many times we
execute it in the verification environment before we publish anything.

**The policy is two agreeing attempts, and it applies to every published result.** Not to repaired
strategies alone, and not to divergences alone. One attempt cannot tell a deterministic recipe from a
lucky one, and the risk that dominates here is **ambient nondeterminism** rather than AI mischief: a
floating dependency range, a mutable tag, a network fetch that happened to succeed. Those hit a
first-attempt success exactly as hard as a repaired one, so exempting the easy path would exempt most
of the corpus.

Attempts run on different workers at different times, share a cache key, and differ in `Attempt`
([`01-architecture.md`](01-architecture.md) §1.1). Both have to agree, and we record both
`EnvironmentDescriptor`s. A disagreement produces `Void { CleanRunsDisagreed }` with a flake note,
and it pages someone.

This doubles the build count, and [`10-scale.md`](10-scale.md) §1 costs it that way. Two levers keep
it affordable:

- **Confirmation is cheap where the first attempt was cheap.** The image, source and dependency
  caches are warm, so a second npm attempt costs seconds.
- **Tiers below `bulk` may run single-attempt**, marked `unconfirmed`, and publish nothing. That is
  the right setting for an exploratory sweep whose output feeds triage rather than attestations.

### 3.1 The repair loop

```
attempt strategy S₀ in the verification environment
  ↳ success → confirmation attempt → agree? → attest
  ↳ failure → classify deterministically (missing toolchain, lockfile mismatch, network denied,
              OOM, timeout, interpreter version, native dep, …)
     ↳ rule-based fix exists?         → apply, retry.  NO MODEL CALL.
     ↳ known-unfixable signature?     → Unsupported / Divergent.  NO MODEL CALL.
     ↳ failure signature seen before? → reuse the cached repair.  NO MODEL CALL.
     ↳ otherwise → Builder(compressed log, strategy, evidence, source excerpts) → Sᵢ₊₁
  ↳ retry in the exploration environment with a decreasing budget
  ↳ on exploration success → re-run the final strategy cleanly in the verification environment
```

**Stop rules**, in order of how much money they save:

- **A failure signature that repeats twice ends the loop.** The cheapest rule available. The model
  has stopped making progress, and further iterations buy nothing.
- Escalate to the strong model **on evidence of progress**, meaning the failure signature changed
  *and* the build reached a later phase. Iteration count is not evidence.
- Hard caps: six iterations, eight tool calls per iteration, 20 minutes wall clock on the AI phase,
  500k input and 30k output tokens per target.
- Keep the prior art's **"tool budget nearly exhausted, respond now, do not call more tools"** nudge
  at iteration N minus 2. Modern models still need it.

## 4. Economics

The same architecture diagram produces a $4,000 sweep or a $168,000 sweep. Engineering discipline
decides which, so treat what follows as requirements rather than optimizations.

### 4.1 Caching keys that generalize

The naive key `(role, model, prompt_version, inputs)`, where `inputs` includes the version, means
**siblings never hit the cache**. Each role needs a key that generalizes:

| Role | Key | Why |
|---|---|---|
| Resolver | **(ecosystem, package)** | The repository is a per-package fact that holds for years. Commit-per-version is a deterministic lookup rather than an AI task. |
| Builder (initial) | **strategy family = (ecosystem, build-system fingerprint, toolchain major)** | "pyproject.toml, setuptools, py3.11" is one template, and the target fills in parameters. |
| Builder (repair) | **normalized failure signature** | "setuptools omits the PKG-INFO trailing newline before version X" is *one* repair covering thousands of packages. |
| Explainer | **normalized diff signature** | ~10 diff classes cover the great majority of mismatches. |

Cache per package, once, amortized across its versions. Never per version. When version *N* and
version *N+1* need different AI reasoning, the strategy representation has a bug and the world has
not changed.

### 4.2 The three levers, in order of size

**(1) Compress the log before it reaches a model, worth about 7 times.** Never send raw build
output. Extract the failing tool, the first error, the last N lines of the failing phase, and the
relevant diff hunks, all by fixed rules. 60k tokens becomes 8k. The prior art truncates to a byte
cap, which leaves most of the win on the table.

**(2) One model call per iteration rather than three, worth 3 times.** The prior art's cycle of
Diagnose, Implement and Clean is a 2024-era workaround. "Clean" is a model call whose job is to strip
markdown fences, followed by manual fence-stripping anyway. "Diagnose" serves observability rather
than accuracy, as their own code comment says, and we get the same artifact by making `diagnosis` a
**required field in the structured output**.

**(3) Prompt structure for caching (2–5× on input).** All roles share a large stable ecosystem
prelude and tool schema. Order every prompt `[stable prelude | stable tools | volatile target
context]` with a cache breakpoint before the volatile part. **Cache-read rate is a first-class SLO,
target > 70%.** Account `cached_input` as a subset of `input`, matching the prior art's schema so
published cost data stays comparable.

On top of that, **route sweep-tier first-pass inference through a batch API** where the provider
offers one. A sweep is a batch workload by definition, and batch pricing usually halves the bill.
Interactive verification and the repair loop stay synchronous.

### 4.3 Admission control

Budgets cap the blast radius; they do not improve the ratio. Expected-value gating does:

- Enter the repair loop only if the failure signature is **novel**, the target's **prevalence score**
  is above threshold, or a human asked.
- **Cold sweeps run in prevalence order**, using a normalized dependency-graph score per ecosystem.
  At 100k targets that decides whether the money goes to packages people import.
- Report **$/verdict gained**, not $/target. If repair costs $0.10 and converts 25% of what it
  touches, that is $0.40 per conversion, which pays. At 3% conversion it is $3.30, and it
  should be off for sweeps while staying on for interactive use.

### 4.4 Expected shape

- **Warm sweep** (a re-run; only new packages and changed failure signatures touch a model): token
  cost lands *below* compute cost. Comfortably affordable.
- **Cold first sweep**: dominated by repair. With the levers above, low thousands of dollars; without
  them, two orders of magnitude worse.

The cost view in the UI ([`11-interfaces.md`](11-interfaces.md) §4) exists so that this is observed
rather than discovered on an invoice.

## 5. The repair→rule flywheel

**The single highest-leverage design element in the AI subsystem.**

Every successful repair is promoted into a **candidate rule** and re-tested corpus-wide before merge:

```
repair succeeds
  → normalize the failure signature
  → generate a candidate: heuristic | stabilizer | flow-template patch | definitions entry
  → run the candidate against the full regression corpus
  → report impact: "would flip 340 targets to pass and 2 to fail"
  → human review (two-party for stabilizers)
  → merge → every future target with that signature is fixed with NO model call
```

Without this loop the system pays for the same insight ten thousand times. With it, model-invocation
rate should **trend down** even as coverage grows, which is why §6 tracks it as a first-class
number.

`trigon strategy annotate-diff` generates the inferred-versus-corrected unified diff that
accompanies each promotion. That one artifact, holding model output, human correction and prose
reason, serves as review aid, eval data and few-shot corpus. Producing it takes one keystroke from
any failed run.

## 6. Evaluation

This determines whether the project survives its first model upgrade.

### 6.1 Three frozen corpora

| Tier | Size | Cadence | Mode |
|---|---|---|---|
| `smoke` | ~50 targets | every PR | **replay only, zero model calls, < 10 min** |
| `regression` | ~500, stratified by ecosystem × failure class | nightly | live model calls, real builds |
| `sweep-sample` | ~5,000 | weekly | full pipeline |

Every corpus is a `PackageSet` with a **canonical content hash recorded on every run**. Without it
you cannot tell an improvement from a corpus edit, so "reproduction rate went up" means nothing.

The `smoke` tier compares against recorded digests, so **a stabilizer change fails the whole tier by
construction**. That is correct, and it needs the `trigon bench regold` workflow in
[`05-archive-and-normalization.md`](05-archive-and-normalization.md) §6 rather than a suppression
flag. A pull request that moves digests carries the regold review artifact and the new
`stabilizer_set_digest`; one that moves digests with no stabilizer change in the same commit is a bug.

### 6.2 Label by required capability, not pass/fail

`trivial-deterministic`, `needs-source-discovery`, `needs-repair-timestamp`,
`needs-repair-path`, `needs-repair-toolchain`, `needs-repair-deps`, `known-unreproducible`.

The reason: a model change that raises aggregate pass rate **while making the model fire on
`trivial-deterministic` targets** is a regression, and a single aggregate number would never show it.

### 6.3 Metrics

| Metric | Direction | Notes |
|---|---|---|
| pass rate by ecosystem and by label | up | the headline |
| **model-invocation rate** | **down** | the flywheel working |
| $/verdict gained | down | |
| iterations-to-success histogram | left-shifting | |
| **flake rate** | zero | re-run identical inputs 3×; any verdict that flips is a **P0 bug in the deterministic layer** |
| **false-mismatch rate** | zero-ish, gated hardest | we said `Divergent` and the package was fine |

False-mismatch is the most expensive error class in the product: it burns reviewer trust, and given
that divergences publish automatically ([`09-attestations.md`](09-attestations.md) §5) it publishes
an accusation. It is an SLO with a **publication kill-switch** rather than a benchmark number.

### 6.4 Replay-based prompt evaluation

Hold recorded tool results fixed, swap the prompt or model, and check whether the new output has the
same shape as the known-good `Strategy`. This catches most prompt regressions at near-zero cost and
with no builds.

It is approximate: expect meaningful fall-through where a new model requests a tool call for which no
recorded result exists. Budget a live tier behind it rather than pretending replay is sufficient.

### 6.5 Shadow mode for model promotions

A new model runs on 10% of live sweep traffic. Promotion requires **zero new failures on previously
passing targets** and **zero verdict flips on `trivial-deterministic`**. Only then is `models.toml`
edited.

## 7. Providers

```rust
#[async_trait]
pub trait LlmProvider: Send + Sync {
    fn id(&self) -> &str;
    fn caps(&self) -> ModelCaps;      // structured_output, tools, context, thinking, batch, cache
    async fn complete(&self, req: Request) -> Result<Response, LlmError>;
    async fn stream(&self, req: Request) -> Result<BoxStream<'static, Chunk>, LlmError>;
}
```

> **Revised in implementation.** The trait is **synchronous**. An async trait obliges every caller
> to hold a runtime, and the two implementations that matter here either block in their own client
> or are a recorded transcript with no I/O at all — a replay harness and a test should not need an
> executor. A synchronous trait is callable from an async context by whoever owns the runtime; the
> reverse is not. `trigon-attest`'s `Signer` was changed for the same reason and a sharper one: the
> verifier build must link no runtime. See [`16-findings.md`](16-findings.md) §3.1.

**Write it: roughly 600 lines over `reqwest`, three implementations.** The Rust LLM-framework
ecosystem is young and churny, and a framework here costs more than it saves.

| Implementation | Covers |
|---|---|
| **OpenAI-compatible** | OpenAI, Ollama, vLLM, llama.cpp, Azure, OpenRouter, Groq and Together, which covers most of "local and multi-provider" in one code path |
| **Anthropic native** | reasoning controls, prompt-cache breakpoints, batch |
| **Google native** | |

`models.toml` maps **role → (provider, pinned snapshot id, budget, fallback chain)**:

```toml
[roles.builder]
provider = "anthropic"
model    = "claude-opus-5"          # exact snapshot, never an alias
cheap    = "claude-haiku-4-5-20251001"
budget   = { tokens_in = 500_000, tokens_out = 30_000, wall = "20m" }
fallback = ["openai-compatible:local/qwen-coder"]

[roles.explainer]
provider = "anthropic"
model    = "claude-haiku-4-5-20251001"
```

Running fully locally means pointing every role at an Ollama or vLLM endpoint. Nothing else changes.

**Structured output is where the multi-provider abstraction hurts.** Provider mechanisms
differ materially and local models are unreliable at all of them. So `ModelCaps::structured_output`
gates a **text-first fallback path**: free-form YAML, then validate-and-repair through
`serde_path_to_error` ([`04-strategies.md`](04-strategies.md) §2.2). Structured output is reserved
for one thing, the final `Strategy`, which keeps the surface that has to work everywhere small.

Retry uses `backon`, and **we own the transience classification**. Nesting provider-SDK HTTP retry
inside our own retry produces multiplicative backoff and unattributable latency; the prior art warns
about this, and the warning holds.

## 8. What replay proves, and what it does not

Every request, response, and tool call is content-addressed into a run transcript, and a run can be
replayed with **zero model calls**.

**This proves provenance of the derivation. It does not prove reproducibility of the result.** It
replays the model, not the world. Say it in those words in any external documentation, because the
stronger claim is tempting and false.

To make even the weaker claim true:

- Store **every tool result byte-for-byte** in the CAS. Tool results embed the world: registry
  responses, git refs, fetched files. A replay missing them is fiction.
- **Pin exact model snapshot ids, never aliases.** An alias that resolves to a new snapshot breaks
  replay, and says nothing when it does.
- Record `{model_id, temperature, top_p, seed, system_prompt_hash, tool_schema_hash, prompt_version}`
  in every transcript.
- **Forbid wall-clock reads in prompt construction**, enforced by a lint, because it is the easiest
  nondeterminism to introduce by accident.

Known limits worth documenting rather than hiding: streaming reassembly can differ; provider-side
prompt caching can subtly alter outputs; default sampling parameters drift between provider versions;
tool-call ids are not deterministic.

Replay earns its storage on three jobs: regression testing, cost-free prompt evaluation, and
auditing *how* a model-assisted strategy came to exist.

## 8b. The third question: an opinion about a diff

The first two questions ask for a strategy, which the run then executes and checks. The third asks
for a *reading*: a run that ends divergent, with a model configured, renders its differing members
— bounded in bytes, text diffed, binary named — and asks whether the difference is plausibly
**substantive** or plausibly **semantically equivalent**. Nothing executes the answer and nothing
checks it, so nothing may depend on it:

- the comparison outcome is already final when the question is asked;
- the publication gate does not read the field, and `trigon-api` has a test that it cannot start;
- no signed statement carries it — an accusation carrying a model's guess would be Trigon signing
  something nobody established.

It is recorded — `RunRecord.diff_opinion`, `run.json`, one panel in the management UI — with the
model's name and the condition it was formed under: how many differing members it was shown, of
how many there were. An opinion over 3 of 300 members is a different claim from one over 3 of 3.
`None` means no model, nothing to show, or the ask failed; it never means the diff is fine.

Who it is for: the reader triaging a corpus of divergences. "Likely a banner timestamp" and
"likely different logic" deserve different afternoons, and until this existed the record could not
tell them apart without a human opening the diff.

## 9. Prompt-injection posture

Package source, README files, CI configuration, registry metadata, and build logs are all
attacker-controlled text reaching a model that holds tools. This is an accepted, mitigated threat
rather than a solved one; the full treatment is [`12-security.md`](12-security.md) §4. The
AI-subsystem half of the mitigation:

- Tools are **read-mostly and capability-scoped** to the run's own workspace.
- `run_in_container` exists **only in the exploration environment**, which already executes the
  package's own build scripts, so an injection gains nothing there it did not already have.
- Model output is parsed into a **typed, validated `Strategy`**, never spliced into a shell command.
- A strategy requesting wider egress or an unpinned image is rejected by validation, not by model
  judgement.
- **Build logs carry the most risk**, because the build script can print anything, including forged
  tool-result framing. We nonce-delimit untrusted content, strip control characters, cap lengths, and
  keep tool results and model text **unforgeably distinguishable** in the transcript format. Without
  that, a log printing fake tool-result JSON could rewrite history during replay.
- Operator instructions go in a proper system-role message, never spliced into user text.

Behind all of that sits a structural backstop. A fully successful injection produces a *candidate
strategy* and nothing more, and that strategy then has to reproduce the artifact twice, in an
environment with no exec and restricted egress, under the artifact-hash check. One attack survives
all of that. [`12-security.md`](12-security.md) §2 covers it, and it is why that check exists.
