Trigon

Does this published artifact correspond to that source?

Trigon downloads a published package, finds the source it claims to come from, rebuilds it in a sealed container and compares the two. It reports in one word how far they agree, and signs that answer so anyone can check it without trusting us.

It rebuilds npm, PyPI, crates.io and NuGet packages today. Comparing two artifacts you already hold needs no network.

Source and artifact

Package registries ship artifacts: a .tgz on npm, a wheel on PyPI, a .crate, a .nupkg. Reviewers read source: the repository on GitHub. The registry does not check one against the other.

Attackers use that gap at build time. A malicious publisher, or an attacker on the build machine, can ship something the source never contained. In event-stream, ua-parser-js and the xz backdoor, the malicious code sat in the published artifact, outside the repository anyone was reading.

Trusted publishing and SLSA provenance record which workflow, in which repository, at which commit, produced an artifact. They do not show that the artifact corresponds to the source at that commit: a compromised workflow or a malicious build script still produces valid provenance. To find the source, Trigon reads the commit a package records about itself where it has one: npm’s gitHead, the <repository> commit in a .nupkg, a crate’s .cargo_vcs_info.json. Then it rebuilds to check the correspondence. Reading trusted-publishing and SLSA provenance is designed (docs/06 §5) and not built.

The limits of a verdict

Trigon does not ask whether a package is safe. A package that builds a backdoor from its own source reproduces, and that is the correct answer. A verdict tells you the artifact is what the source makes; you still judge whether the source is any good.

On npm, tarballs come close to full reproducibility with no link to their source, so a wall of green on an npm lockfile is true and close to worthless. The npm question worth asking is source attribution: whether the tarball corresponds to the repository it claims.

How it works

Rebuild it in a box

Trigon finds the source at the right commit, works out a recipe (a strategy: install these dependencies, run this build) and runs it in a podman container. The recipe is data, so Trigon can store, compare and replay it.

The mirror is the only way out

During the build the container can reach one thing: a mirror of the registry as it stood when the publisher released the package, so each dependency resolves to the version the publisher got. The mirror hashes and records everything it serves. If the build downloads the artifact Trigon compares it against, Trigon marks the run void. This is the mirror-only egress tier. At the default, open, the build can reach the internet, and the run publishes only as void.

Stabilizers remove harmless noise

Two honest builds of one source rarely match byte for byte. Each stabilizer removes one known kind of harmless difference, such as a timestamp or the order of files, the same way on both sides, and reports what it changed and how risky the change is. The report names every stabilizer that fired, so you can see when one you reject was used.

One word for the answer

The comparison ends in one of four outcomes, strongest first. On the wire each outcome is its string name.

outcomemeans
✔︎exact The raw bytes are identical, before any stabilizer ran.
✔︎normalized The stabilized forms are identical, and every stabilizer that fired ships with Trigon and is no riskier than metadata: timestamps, ordering, file modes.
◐normalized_with_caveats The stabilized forms are identical, but a stabilizer that fired changes content, or a person or a model wrote it. Read what fired.
✖︎divergent The stabilized forms differ, and Trigon names which files.
⊘void Outside the four. The run proves nothing, and Trigon records why: the build could reach the open internet, it reached the artifact Trigon was comparing it against, or a stabilizer that a person or a model wrote fired.

trigon verify prints the four outcomes in these glyphs and colours. trigon check adds ⊘ for void, and colours normalized_with_caveats green with the other passes. The word and the glyph carry every distinction the colour does, so output without colour keeps them all.

Signed and published

Trigon signs its answer as an in-toto statement in a DSSE envelope. Anyone holding the two artifacts can re-run the comparison with a verifier build that has no network client. trigon publish writes the answers the publication gate allows to an evidence repository, an ordinary git repository with an append-only signed log. A consumer clones it and queries it locally, so a thousand-package lockfile costs no request per package, and no server learns which packages you use.

Search and judgement, kept apart

When Trigon finds the source, guesses the recipe or repairs a failed build, it is searching, which can be messy and may use the network or a language model. When it decides whether two artifacts are the same, it is judging, which must be exact and repeatable. A language model can help the search when you name a provider; the crates that judge link no model code.

The judgement half links no network client, no async runtime and no model code. cargo run -p xtask -- policy fails the build if that changes, and the verifier build, cargo build -p trigon --no-default-features, contains only this half. Its line coverage is 88.4% whether or not the tests that need a network run, so tests that open no socket reach every line the suite covers there.

Trigon signs in a separate step, on purpose: trigon rebuild runs a stranger’s build scripts, so the key belongs to another process. trigon attest reads the stored bytes back by hash and re-derives the verdict before it signs. Trigon publishes a verdict only after a second, independent attempt agrees: on another machine, or on the same machine starting cold where the repository sets same_host_confirmation = true, as the end-to-end script does.

Evidence anyone can check

Signed statements

trigon attest signs in-toto statements in DSSE envelopes, in a process that runs no build and opens no socket. It fetches both artifacts from the store by hash, recomputes the comparison, and refuses to sign if the answer differs from the run’s record. For a run the publication gate calls void (its guard tripped, it ran at open egress, or a stabilizer somebody wrote fired), it signs void/v1 and nothing else, which says why and never which way the comparison went. For any other run it signs equivalence/v2 or divergence/v2, beside rebuild/v1 and buildobservation/v1.

A repository with an append-only log

trigon publish asks the publication gate about each run and writes what it allows to a git repository: the signed records, the evidence needed to re-derive each one, an index, and an append-only log whose checkpoint trigon log sign signs. It makes one commit per publication and never force-pushes. Nobody edits a published record: to correct one, you publish a new record that supersedes it, and both stay in the log.

Checking a lockfile

A consumer trusts a repository once, by pinning its log key and its attestation key. trigon evidence sync verifies each clone whole, and refuses a checkpoint that does not extend the one it accepted before. After that, trigon check answers every package in a lockfile from the clone, with no request per package, so no server learns which packages you asked about. It reads package-lock.json, npm-shrinkwrap.json, requirements.txt and SPDX JSON.

A package no source holds a record for reads never checked, and never counts as a pass. The exit codes are for CI:

0
every package is at or above the threshold
1
a divergence
2
a package never checked, or withdrawn
3
a void, or a result below the threshold you set with --min or --max-risk
4
a deleted record, a record or source that failed verification, a required source that is unknown, or a package no source could answer
5
Trigon could not run the check

Checking a verdict yourself

Each published verdict carries the command that would falsify it. Run that command with the two artifacts and it re-derives the verdict from the bytes, then checks the published comparison report against it, member by member. If someone changes one byte of a record, verification fails, because no leaf of the log names it.

--lookup reads a synced clone and fetches the evidence it re-derives from, so it belongs to the full build. The network-free verifier build carries eight commands, and checks a record with --record <file> and --evidence <dir> instead. Its dependency tree holds no tokio, reqwest or hyper:

Not built or not settled yet

  • No public evidence repository exists yet, and the client ships no default source. Both wait on one decision, the repository’s owner and namespace (docs/19 D3). Until then you configure a source yourself, such as the local repository the end-to-end script creates.
  • By default trigon publish refuses every divergence. A divergence is a public accusation, and notifying the maintainer has no channel until docs/19 D7 decides one. A repository that sets divergences = "feed" publishes each divergence with an entry in feed/divergences.atom.
  • Trigon has no witnessing yet (docs/19 phase 7b). Until witnesses cosign checkpoints, the log’s owner can rewrite the log, and only a client that kept an older checkpoint, or one comparing mirrors, will notice.
  • A statement carries no third-party time, so a verifier cannot tell when the signer signed it, and nothing limits what a stolen key can sign until the maintainers settle docs/19 D6 (threat model D24).
  • Trigon has no standalone npx trigon-check or uvx trigon-check client yet (docs/19 phase 9), and no published release. To check a lockfile today, you build Trigon from source.
  • scripts/evidence-spike.sh publishes against a scratch GitHub repository. Nobody has run it yet: it needs a repository the owner has yet to name.

Ecosystems and status

Trigon rebuilds four ecosystems today. Each rate below names the corpus it came from.

npm, PyPI, crates.io and NuGet have registry clients, so Trigon resolves, fetches and rebuilds their packages. The design covers RubyGems and GitHub releases, and they come next; until then Trigon refuses a target in either by name. trigon verify compares two files from any of them and chooses the stabilizer set from the file name. With the gem set it compares two .gem files, but Trigon cannot yet resolve or rebuild a gem. An npm tarball takes the generic tar-gzip set, because nothing inside a .tgz says whose it is; pass --profile npm-tarball to select the npm set.

Sixteen of npm’s 65 targets that reached no comparison were our fault: a missing tool, a workspace: protocol npm does not speak, a workspace sibling the recipe did not build first. The reproduction rate leaves them out by design and the reach figure counts them, so read reach as a floor.

crates.io and NuGet have no rate, because neither has a stratified corpus yet. Both rebuild end to end at mirror-only. Of the twelve crates we have tried by hand, six reproduce, hashbrown@0.17.1 and serde@1.0.219 among them; each remaining divergence is the Cargo.toml manifest rewrite that backlog item B20 is about.

A rate describes the pipeline on one corpus. The strata are weighted by build system, not by how common each build system is, so neither total says how much of an ecosystem reproduces. docs/15-corpora.md argues why the strata matter more than the totals.

Get started

Rust 1.85 or later, edition 2024. Rebuilds also need podman.

Build it

Compare two files you already have

This runs offline, with no container. The exit code is 1 for divergent and 0 otherwise, so it drops into a script.

Rebuild a package behind the mirror

Build the two helper images once: a base image to build in, from a parent pinned by digest, and the image the mirror runs from. At --egress mirror-only, --image auto uses a base image already on the machine and refuses to build one. --timewarp auto pins the mirror to the moment the publisher released the package, and --store keeps the run so a separate process can sign it.

Run the whole loop

scripts/evidence-e2e.sh creates keys and a local evidence repository, rebuilds a package behind the mirror, confirms it with a second cold build, publishes the verdict, then checks it the way a consumer would, including two checks that must fail. It needs the base image from the step above, and builds the mirror image itself if it is missing. It takes a few minutes, needs podman and the network the mirror fetches through, and keeps everything it makes in work/evidence-e2e/.

Build the verifier

For checking somebody else’s claim. It writes the same target/release/trigon as the full build, so give it a target directory of its own, as scripts/cross-machine-verify.sh does.

Then read Using Trigon, the task-oriented guide, starting with its section on what a verdict does not tell you.
